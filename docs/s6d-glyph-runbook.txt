## What it draws

Five 8x8 PutImage cells, one per 64 KiB window, at the same origins as
the rectangle client: (16,16), (16,120), (16,220), (16,320), (16,420).
The top-left 5x7 of each cell is a digit, 1 through 5. Ink is index 15.
The other pixels in the cell are index 0. No StoreColors, no
FBIOPUTCMAP, no fonts, no ports.

Index 15 is the pixel value in the shadow. It is not a measured DAC
colour. The watched squares used indices 1, 2, 4, 14, and 15, and the
top index-1 square was the one that may blend into the field. This
client does not use index 1. If 0 and 15 happen to be the same colour
in the current DAC, the panel will not show the digit. That result
would be a palette fact. This client cannot create the contrast.

GetImage reads the server pixmap. On Xfbdev that pixmap is the RAM
shadow, not the panel. A match does not prove the glass, a keyboard,
or a hue.

An 8x8 at x=16 is 32-bit aligned. `shadowUpdatePacked` copies each
damage box top to bottom. These five boxes do not share a row, so the
region keeps five rectangles. The host test walks every pixel through
`wd24s6d_livelock_span` and `wd24s6d_thrash_note` with bound 32.
Result: 678 passed, 0 failed, 320 bytes, maximum consecutive window
switches 1. That is the copy of these cells, not a full-frame fill.
320 is the whole paint. The frame is 640 times 480.

An untouched 8x8 at (300,40) is read before the PutImages and again
after. It must be unchanged. That is the geometry control.

## Host Xvfb, qemu -cpu 486

qemu-i386 8.2.2 `-cpu 486`. Xvfb `-nolisten tcp -noreset`, no `-ac`.
Not wd24s6d and not the panel.

Against `640x480x8`, stdout and status:

```
WD24X-GLYPH shadow 640x480x8 marks 5 match 5 ctrl 1
```

RC 0.

Against `800x600x8`:

```
WD24X-GLYPH bad geom 800x600x8 bpp 8
```

RC 1. The client stops. It does not draw.

The alarm is 15 seconds. A later target script, if one is written,
must keep `-noreset`, must not pass `-ac`, and must not start a second
X after a nonzero client status.

## Trigger script

`docs/s6d-glyph-run.sh`
Artifact `/opt/cursor/artifacts/wd24x-glyph-run.sh`

Copying it does not run it. Do not set `WD24X_MOCK`. The rectangle
client is not on its command line and is not removed.

On the target, after the files are already in `/tmp` and a person says
to trigger:

```
sh /tmp/wd24x-glyph-run.sh
```

It checks the baseline module hash and the glyph hash, empty `/proc/fb`,
vtcon0 `(S) VGA+` bind 1, no vtcon1, and no `/tmp/.X1-lock` or
`/tmp/.X11-unix/X1`. It does not delete a stale X1 socket. A failed
check does not insmod.

insmod parameters are `dryrun=0 live=1 mode=640x480-8 trial=180 s6d=1
pattern=0 fix_sr06=1 s6d_fbcon=1 s6d_bind=0`. X is
`Xfbdev :1 -nolisten tcp -noreset -fb /dev/fb0`. No `-ac`.

Timing on the success path: 15 s for X to stay up, 20 s to watch the
client, then X is reaped, then 150 s so the 180 s trial can expire,
then `/proc/wd24adv/live` must show `trial expiry`, `mismatches 0`, and
`in_text 1`. Then rmmod. The pass line is exactly

```
WD24X-GLYPH shadow 640x480x8 marks 5 match 5 ctrl 1
```

as the only stdout line, and `CL=0`. Anything else stops the series.

A client failure, a client still running at 20 s, or a dead X does not
take the 150 s wait. Those paths still TERM the recorded pid, one
KILL, and rmmod when the pid is gone. If that pid is still alive after
the KILL and 5 s, the script does not rmmod and does not remove the X1
socket. The executor finishes that. Logs, the glyph binary, the module,
and the archives are left in place.

This script does not prove the panel or the keyboard. thrash must stay
0. Do not raise the bound and do not load the colormap candidate.
