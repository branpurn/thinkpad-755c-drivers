Phase 2 and phase 3 passed at 16:15 ET on `fdf30c77` with the `a143000`
scripts. Leave `docs/s6d-candidate.env` on that file. Desktop and Doom
both load the module named in `docs/s6d-desktop.env`. That build must
compile on 6.18.57, where `lock_fb_info()` returns void. It also has
the present ioctl. A second open of `/dev/fb0` while X is mapped
returns `-EBUSY`, and the close drops X's pages. `/proc/wd24adv/cmap`
is the published cache, which is what `FBIOGETCMAP` would return, and
it is filled only after `fb_setcmap` read `3C9` back. The proc does
not touch a port.

At 18:10 ET, `c6ca389` did not compile (`lock_fb_info` used as an int)
and Doom on `fdf30c77` took `Bus error`. The mmap path faults once per
64 KiB window and never faults twice in the same window, so the
consecutive-switch counter reaches 32 within the first frames and the
fault returns SIGBUS. The bound stays 32. The timedemo does not mmap.
`WD24X_DOOM_FB=ioctl` sends the 320x200 buffer. The kernel programs
each 64 KiB window once and writes it with 32-bit stores. `present
switches 5` is that count. `zone memory: ... 600000` is the engine's
`%x` of 6 MiB. `couldn't open demo1.lmp` is the external-file probe;
play continues from the wad.

Nothing here writes a speculative VGA register. Each script hash-checks
its inputs, stops on the first failure, and waits out the trial so text
comes back with mismatches 0. `trial` cannot exceed 600.

## What the Win98 run compares

Same wad. Vanilla defaults: screen size 9 (status bar visible), high
detail (`detaillevel` 0). No custom config. `doom -timedemo demo1`,
then demo2 and demo3 the same way. Our command does not pass a screen
size and does not load a config, which is that default in this engine.
The script prints `WD24X-DOOM-FPS gametics N realtics N fps_x100 N`
with `fps_x100 = gametics * 3500 / realtics` (35 Hz). A completed
timedemo exits 255 because the engine reports the timing through
`I_Error` and then `exit(-1)`. That 255 plus the `timed N gametics in
N realtics` line is success, not a driver fault. No fps number in this
tree is the bar. The Win98 timedemo on this machine is the bar.

The timedemo blit is letterbox, 320x200 doubled into the 640x400 band
at rows 40..439, done in the kernel. Five window programs per frame.
Two source pixels per aligned 32-bit store. No mmap fault on that
path. `WD24X_DOOM_FB=mmap` still exists and is not what the script
sets. Fill stays available and is not the timedemo.

## Order

One script at a time. `/proc/fb` empty, no X socket, no `wd24adv` in
`/proc/modules`. Copy the script next to its env file and run it with
`sh`. The Doom script also needs `s6d-desktop.env` in that same
directory. Do not export `WD24X_MOCK`.

1. Desktop, after the new module and `wd24x-xcmp` are pinned.
   `sh /tmp/s6d-desktop-run.sh`
   Xfbdev `:1 -nolisten tcp -noreset -fb /dev/fb0`, then the glyph
   client (indices 0 and 15), then QueryColors against
   `/proc/wd24adv/cmap`. Trial 180. Pass is all of:
   `WD24X-GLYPH shadow 640x480x8 marks 5 match 5 ctrl 1`
   `WD24X-XCMAP entries 256 shift10 1`
   `WD24X-CMAP-CACHE entries 256 shift10 1`
   `WD24X-DESKTOP-RUN cmap match 256`
   `wd24adv live: trial expiry -> 0`
   `readback mismatches 0`
   `in_text 1`
   `WD24X-DESKTOP-RUN done`
   This is not a long-lived X session and not a panel reading of hue.

2. Doom timedemo, after the new module and `wd24x-doom` are pinned.
   Do not use `fdf30c77` for this. `sh /tmp/s6d-doom-run.sh demo1`
   Then, only after `WD24X-DOOM-RUN done`, `demo2`, then `demo3`.
   Each is its own insmod, trial 600. Input stays off. Pass adds
   `WD24X-DOOM fb ioctl 320 200`,
   `WD24X-DOOM present switches 5`,
   `WD24X-DOOM blit letterbox dword`,
   `WD24X-DOOM palette put 256`,
   the gametics line, and `WD24X-DOOM-RUN done`.
   `/proc/wd24adv/s6d` grows `present frames N last 5 total ...`.
   Faults stay 0. The thrash latch stays clear.

3. Normal play, only while someone is watching the panel.
   `sh /tmp/s6d-doom-run.sh eyes`
   That one sets `WD24X_DOOM_INPUT=tty`. It does not call `KDSETMODE`.
   Quit from the keyboard if the keys work. If they do not, the trial
   still ends the mode at 600s.

## If it stops

The script's `stop` line is the reason. Do not insmod again over a
loaded module, and do not start the other script until the console
line is VGA+ bind 1 and `/proc/fb` is empty.

If the shell still answers and the trial has not expired, wait. Do not
kill `-9` a mapped client unless the script already did: `SIGKILL`
skips the server's `KD_TEXT` ioctl. The module trial is the text
restore. `rmmod` after a clean script prints `RM=0`.

If the shell is dead, that is the power-cycle. It is the one step that
is not on the serial line.
