## Box follow-up 2026-11-05 ~19:20 UTC — root cause + safer restore (755C untouched)

### Why pattern=0 produced a green line roll (not colour bars)

`pattern` is a **bool** module param (default 1), not a pattern id:
  - `pattern=1` → after mode set, `wd24_pattern()` draws 16 vertical BIOS-text-colour
    bars over the whole 640x480 frame (banks 0-4; reversed from row >= 256 KiB).
  - `pattern=0` → skip `wd24_pattern` entirely (`hw_run` OP_MODE: only call when
    `pattern && wd24_has_pattern(m)`).

The READY command in WD24ADV-NEXT-STAGE intentionally used `pattern=0` to
"avoid colour-bar path" so the first S6d visual proved arm/register alone.
So no bars was correct for that command — not a wrong pattern id.

What Brandon saw instead:
  1. Mode set leaves VRAM without bars (pattern skipped).
  2. `s6d_arm` → `register_framebuffer` → fbcon binds (CONFIG_FRAMEBUFFER_CONSOLE=y,
     no DEFERRED_TAKEOVER).
  3. fbcon clear/redraw calls `s6d_fillrect` / `s6d_imageblit`: pixel-by-pixel
     `writeb` under `hw_lock`, banked via SETWIN. That paints **line-by-line**
     slowly across the panel → the green roll (BIOS text DAC still loaded;
     S6d has no `fb_setcolreg` yet, so fbcon colour indices hit the leftover
     DAC — often reads as green on this panel).
  4. Further fbcon clear → white; then imageblit of the TTY line (80x30).

### Why serial/keyboard died — NOT ESTABLISHED (see the audit below)

An earlier note blamed a blocking `/proc/wd24adv/live` `mutex_lock` while
fillrect held `hw_lock`, plus the POST `head` of `/proc/wd24adv/*`. That is
not shown. Those reads were typed before `insmod` returned, so the shell
had not executed them. The hang audit later in this file is the current
account. Do not treat the proc-lock story as the cause.

### Box fixes (this follow-up)

  - `live_read`: `mutex_trylock`; if busy, return a short non-blocking message
    (never hang `head`/`cat`).
  - `control_write`: `mutex_trylock` → `-EAGAIN` if busy (restore cmds retry).
  - `s6d_fbcon` (bool, default 1): `0` arms dual-window but skips
    `register_framebuffer` so bars/`pattern` stay for the trial window.
  - Docs: pattern is bool; no-overlap rule for /proc during visual; next LIVE
    steps in WD24ADV-NEXT-STAGE.md (Brandon watching required).

## Hang audit (the ~13:50 visual, commit 9ad254f) — 2026-11-05

Observed, and only this:

- printk: load 0, mode 0, then `Console: switching to colour frame buffer device 80x30`, then `S6d: armed + registered fb0`.
- `echo RC=$?` never returned.
- Owner: green line-by-line roll, then a white screen with fbcon text. No colour bars (`pattern=0`).

- POST lines that read `/proc/wd24adv/*` were sent before the insmod prompt returned.

Not a PASS beyond the registration printk. Mode set and `register_framebuffer` returning far enough to print "armed + registered" are what that printk shows. Restore was not observed.

Code at 9ad254f, checked against Linux 6.18.7 (same line as 6.18.57; fbcon/vt sources are not in this repo, they were read from the stable tree):

1. `pattern` is a bool. `pattern=0` skips `wd24_pattern`. No bars on that command is what the code does.
2. `do_bind_con_driver` prints `Console: switching to ...` and then calls `update_screen`, which is the fbcon redraw. That runs inside `register_framebuffer`, before `s6d_arm` prints "armed + registered". The line-by-line roll is the timing of that redraw through `s6d_fillrect` / `s6d_imageblit` (one `writeb` per pixel). Calling the green colour "the BIOS DAC" is a hypothesis: this driver has no `fb_setcolreg`, so the DAC is whatever was already loaded, and the owner saw green then white. The hue is not proven from the registers.
3. There is no per-fb flag that skips the bind. `fb_info.skip_vt_switch` only calls `pm_vt_switch_required`. `CONFIG_FRAMEBUFFER_CONSOLE_DEFERRED_TAKEOVER` depends on `FB=y`; this kernel is `FB=m`, so `deferred_takeover` is compiled out. The switching printk shows the bind ran.
4. After register returns, `s6d_arm` takes `hw_lock` and `pr_info`s the armed line while still holding it. The 755C boot line in WD24ADV-LIVE-TEST is `console=tty0 console=ttyS0`. The S6d floppy APPEND file is not in this repo, so that exact cmdline was not re-read here. If tty0 is a printk console, the flush calls `fbcon_putcs` → `s6d_imageblit` → `mutex_lock(hw_lock)` on the same task. The mutex is not recursive. The task sleeps holding `hw_lock` and `console_lock`. `insmod` never returns, so the shell never runs the typed proc reads. `trial_fn` also needs `hw_lock`, so the 30 s restore does not run. That matches: armed line visible on serial (serial console flushed, then the VT console re-entered), no RC, no restore, keyboard dead (VT needs `console_lock`), serial bytes echoed by the tty and not read.
5. The proc-lock story does not explain this. The reads were not executed.

A read-only preflight later the same day (15:49 America/New_York) recorded this boot's command line with both `console=tty0` and `console=ttyS0,9600n8`. That is the tty0 printk path on the current boot. It does not replay the hang. SysRq was ignored during the hang; whether `CONFIG_MAGIC_SYSRQ` is enabled was not checked.

The same preflight: `uname -r` `6.18.57-tc755x`; `/proc/fb` empty; only vtcon0 `(S) VGA+` bind 1; `fb` loaded and unused, `font` used by `fb`. No frame-buffer vtconsole. Current dmesg ring had been cleared and still contains the earlier `s6d_fbcon=0` arm line. No insmod was performed.
