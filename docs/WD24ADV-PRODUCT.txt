wd24adv product roadmap. wd90c24fb is not part of this work and is not
modified. The trial timer is the development net. It is not the product.
The product is a normal fbdev driver: modprobe brings up the console,
startx brings up the desktop, Doom runs. That default stays dry-run
until the milestones below have passed on the 755C. Guessed registers
are not added. A new port write needs a public source already cited
here and a read-back plus restore in the same gated script.

Sources already used by this tree, and the ones a later stage may use:

- docs/WD90C24.md. The 640x480x8 packed settings are the XFree86
  256-colour values (CR13, CR14, CR17, PR4, PR31, PR30A) at the
  25.175 MHz clock. BITBLT there is the XFree86 wd90c31BitBlt sequence
  on the 23C0h block. MCLK (PR68 bits 2:0, PR69) is explicitly not
  programmed.
- docs/ROADMAP.md. Points at XFree86 3.3.6 SVGA `wd`, the VGADOC
  Paradise chapter, and 86Box `vid_paradise.c` for banking and the C31
  blitter. Those are references, not a licence to copy an unproven
  sequence into wd24adv.
- docs/WD24ADV-DESKTOP-DESIGN.md. Public WD90C31/C24 books, XFree86, and
  live proofs on this machine. No IBM register sequence is in this
  repo. The S0 engine (23C0h block 1 BITBLT, block 2 cursor) is host
  only. `WD24X_LIVE_ALLOWED` is 0. test_engine refuses any live source
  that names that engine. Cursor registers are marked UNPROVEN there.
- Live proofs already on the 755C: text save/restore, 640x480-8, S6
  banking, S6d mmap, and the 16:15 ET colormap pass (publish, one PUT,
  GET, expiry, rmmod). S4/S5 BITBLT logs exist as experiments. They are
  not wired into fb_copyarea.

What stays out until its own milestone: panel power (PR57, PR4 b5),
routing (PR18/PR19), clocks (PR68/PR69), 800x600, DPMS, and the
hardware cursor. wd90c24fb already has blanking and APM. wd24adv does
not copy those sequences across.

## M0 — in this tree

6.18.57 `lock_fb_info()` returns void. The cmap proc does not use a
return value. `WD24S6D_IOC_PRESENT` is the blit. It accepts only
LETTER2X: 320 by 200, scale 2, destination 0,0, 64000 bytes. Any other
width, height, scale, op, or size returns -EINVAL and programs no
window. The accepted op writes the 640x480 frame with one window
program per 64 KiB and 32-bit stores. It does not call the thrash
counter. The bound stays 32. The mmap path is unchanged and is not the
Doom script. Phase 2 and 3 stay on `fdf30c77`.

## M2 — fbcon, still under trial

Script: `docs/s6d-fbcon-run.sh`. It is not part of the module already
built for the desktop and Doom run. One insmod with `s6d_bind=1`,
`s6d_cmap=1`, trial 180. It writes one line to `/dev/tty0` and does
not start X. Pass: session ON, thrash 0, latched 0, expiry 0,
mismatches 0, in_text 1, VGA+ bind 1, `WD24X-FBCON-RUN done`.
Scroll speed is not judged here. `fb_copyarea` is still empty, so a
scroll is a CPU fill through the bank window.

## M3 — X start and stop, still under trial

The desktop script in M1 is the short form. M3 repeats it once more
and then one longer client, still inside the trial, still no second
fb open. Pass is the same cmap match and the same text restore.
A VT switch away and back is a separate insmod, not piled onto a
failed one.

## M4 — BITBLT for fb_fillrect and fb_copyarea

The one-shot already ran. `docs/s4-live-2026-11-05.txt`: 11 of 11
operations verified, idle polls 0, restore 1002/1002, mismatches 0.
That sequence is the XFree86 wd90c31BitBlt path cited in
`docs/WD90C24.md`. `accel=0` (the default) keeps the CPU window for
fills and does not copy. `accel=1` programs one rectangle with the
same parameter order as that table. The gate is
`docs/s6d-accel-run.sh`: the 64x16 fill at (16,112), colour 0x3c,
which is S4 operation 1, on screen in bank 1. CPU bytes, then the
programmed fill, then those bytes are put back. Pass is
`accel 1 gate 1 match 1024` and the usual text restore.

A timeout after the start does not touch video memory and does not
fall back to the CPU. The module stays loaded until a power cycle,
the same rule as the S4 one-shot. A refusal before the start does
fall back to CPU stores. Glyphs stay on the CPU: the S5 guard accepts
only its canned host words, not an arbitrary bitmap.

fbcon scroll uses that copy when `accel=1` is still on after the gate
(`FBINFO_HWACCEL_COPYAREA`). `ypanstep` stays 0: the S4 sequence does
not program a CRTC start. `docs/s6d-scroll-run.sh` is the fbcon bind
with the same gate, then one line on tty0.

## M5 — hardware cursor

`cursor_gate=0` by default. `docs/s6d-cursor-run.sh` is the one canned
show: pattern at 0x50000, the 755C centre register line, 3 seconds,
then the snapshot and the pattern bytes back. Pass is
`cursor 1 show 1 regs 8 vram 256 restored 1`. `fb_cursor` is not
connected: the guard allows that one program and not a moving pointer.
`docs/WD90C24.md` has the register list.

## M6 — 800x600x4 external, blank, DPMS, APM

Not started. Those modes are UNPROVEN in the wd24adv table. Blank and
APM stay in wd90c24fb until a cited sequence is gated on its own.

## M7 — drop the trial harness as the default

Only after M1, M2, and M3 pass, and only in a commit that says so.
`debug=1` keeps the timer. Until that commit, `dryrun=1` remains the
default and a live load still requires `dryrun=0 live=1`.

Eyes-on, after the serial gates, in one sitting: hue of the X desktop,
fbcon scroll, Doom smoothness, and the keyboard. The serial scripts do
not decide those.
