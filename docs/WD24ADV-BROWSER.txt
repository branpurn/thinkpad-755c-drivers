Framebuffer browser for exercising wd24adv. Decision from the
upstream trees read on 2026-11-22, not from the project homepages
where they disagree with the source.

## Choice

Use the NetSurf framebuffer frontend (`nsfb`), not Dillo.

Dillo 3.2.0 is the Tiny Core 16 x86 extension `dillo.tcz` (info Size
544K). Its dep file lists `wget.tcz`, `fltk-1.3.tcz` (FLTK 1.3.11,
info Size 500KB), `dejavu-fonts-ttf.tcz`, `mbedtls3-lib.tcz`, and
`libwebp1.tcz`. Upstream `doc/install.md` requires FLTK 1.3 and names
libpng, libjpeg, libwebp, and brotli as well. The Tiny Core 17 x86_64
build log links FLTK as `-lfltk -lXcursor -lXext -lX11`. The x86
`dillo.tcz.info` says it was tested on Xorg and Xvesa. There is no
framebuffer frontend in that install document. GitHub issue 453 asks
for a framebuffer build and points at NetSurf's frontends tree; it
does not add one. Dillo on this machine would be an X client. That
does not exercise the 8bpp fbdev path.

NetSurf's framebuffer frontend is `frontends/framebuffer` and the
binary name in its Makefile is `nsfb` (installed as `netsurf-fb`).
It links `libnsfb` and optionally FreeType. The internal bitmap font
is selected with `NETSURF_FB_FONTLIB=internal` (`FB_FONT_internal_ns-sans`
in that Makefile). Image handlers are compiled from
`content/handlers/image/Makefile` when `NETSURF_USE_PNG`,
`NETSURF_USE_JPEG`, and `NETSURF_USE_GIF` are on: `png.c`, `jpeg.c`,
`gif.c`. GIF and BMP go through NetSurf's `libnsgif` and `libnsbmp`,
not giflib.

`libnsfb` master `a287525eeafa4b9e721822670e1e03eeeef6b31c`
(2026-11-15) `src/surface/Makefile` builds `surface.c` and `ram.c`
always, and adds `sdl.c`, `x.c`, `vnc.c`, or `wld.c` only when that
library was detected. The README lists SDL 1.2, libxcb, wayland-client,
and libvncserver. It does not list a Linux fbdev provider.
`src/surface/linux.c` was removed in commit `b2bb565` (2018-07-29,
"remove broken surface handlers for ABLE and linux framebuffer
interface"). The parent of that commit is
`51d3ee85de73949483af79671fe9075a10e405e3`. `tools/wd24-browser/patches/libnsfb-linux-fbdev.patch`
puts a small `linux.c` back and adds it to `SURFACE_HANDLER_yes`.
It opens `/dev/fb0` (or a parameter that starts with `/`), reads
`FBIOGET_FSCREENINFO` and `FBIOGET_VSCREENINFO`, and `mmap`s
`line_length * yres`. The original checked the map against NULL and
called `munmap` with length 0. This copy checks `MAP_FAILED` and
keeps the length. For 8bpp it builds the libnsfb cube with
`nsfb_palette_generate_nsfb_8bpp` and programs it with `FBIOPUTCMAP`.
Each 8-bit channel is stored as `(c >> 2) << 10`, which is what
wd24adv's DAC read of `channel >> 10` turns back into the top 6 bits.
Keys come from a raw tty (canonical and echo off, one byte, `poll`).
The mouse is not wired. `ram.c` still allocates a heap buffer. The
8bpp plotter writes index 0 when `palette` is NULL, so the same patch
creates that palette on the ram surface. Without it a ram 8bpp frame
stays zero.

8bpp is still in the plotters. `src/plot/Makefile` compiles `8bpp.c`
next to `16bpp.c` and the 32bpp files. The SDL surface accepts
`bpp` 8, 16, or 32 and, for 8, calls `nsfb_palette_generate_nsfb_8bpp`
and `SDL_SetColors` for 256 entries. That palette is SDL's, not the
VGA DAC. The linux surface above is the path that programs the DAC
through `FBIOPUTCMAP`.

The Tiny Core 16 x86 extension `netsurf.tcz` is version 3.11, info
Size 2.3M, tags gtk2, and the comment says "This version works only
with Xorg." Its dep file lists `gtk2.tcz` (2.24.33, info Size 2.3MB),
`curl.tcz`, `librsvg.tcz`, `glibc_gconv.tcz`, and `libwebp1.tcz`.
Those Size fields are each squashfs, not the transitive X stack.
That extension is the wrong frontend.

## RAM

36 MB is the whole machine, 36*1024 = 36864 KiB. The qemu-user
smoke below peaked at 16400 KiB, and that figure includes the
emulator. JavaScript stays off. The internal bitmap font avoids
FreeType and a font file.

## Build

`tools/wd24-browser/build.sh` downloads the musl.cc toolchain
`i486-linux-musl-cross.tgz` (110230922 bytes, 23 Nov 2021, GCC
11.2.1 20211120) and checks SHA-512
`0a6e508d919d2b5404e53c5bad7ea10924967c4b528012495ecc41ca3f4b371a0da4d814a2a5a18e079b1c330fa808ab0eaa924a3571f3792bcf9004feee856c`.
It then checks SHA-256 of zlib 1.3.1
`9a93b2b7dfdac77ceba5a558a580e74667dd6fede4585b91eefb60f03b72df23`,
the GitHub tag archive of libpng 1.6.47
`631a4c58ea6c10c81f160c4b21fa8495b715d251698ebc2552077e8450f30454`,
and IJG `jpegsrc.v9f.tar.gz`
`04705c110cb2469caa79fb71fba3d7bf834914706e9641a4589485c1f832565b`.
Library commits are pinned in the script. Flags are
`-O2 -march=i486 -mtune=i486`. Upstream makefiles also pass `-Werror`;
the script appends `-Wno-error` so GCC 11 warnings do not stop the
link. `Makefile.config` turns curl, OpenSSL, duktape, webp, jpegxl,
svg, and librosprite off, and turns PNG, GIF, JPEG, and BMP on.

Host tools the script checks before it downloads anything: `git`,
`curl`, `make`, `gcc`, `perl`, `pkg-config`, `gperf`, `flex`, `bison`,
`file`, `readelf`, `sha256sum`, `sha512sum`, `tar`,
`qemu-i386-static`, `/usr/bin/time`, and a host `libpng-dev`
(`/usr/include/png.h`, for `convert_image`). A missing one stops with
`WD24X-BROWSER stop host deps:`.

The build identity is fixed: `HOSTNAME=tc32`,
`SOURCE_DATE_EPOCH=1794996956` (the netsurf pin's commit time),
`WD24X_BUILD_USER=tc32`, `WD24X_BUILD_ROOT=/src/netsurf/`, and
`-ffile-prefix-map` for the source and prefix. The testament patch is
`tools/wd24-browser/patches/netsurf-repro.patch`. The stripped binary
does not contain the build account, the build hostname, or the build
directory.

The script writes `/tmp/wd24-ns-prefix/nsfb/`:

- `nsfb`, 3358656 bytes, sha256 `531803c04944918491480e4add46641c5a91ee0d1dc8841fab81cc1098c7f446`
- `nsres/`, the English resource set: shared files plus `en/`, not the other locale directories
- `pages/`, the canvas page and its images

`readelf -h` reports `Machine: Intel 80386`. There is no `INTERP` program header. objdump of that file showed no cmov, endbr, rdtsc, cpuid, syscall, or sysenter.

Smoke was `qemu-i386-static -cpu 486` on the ram surface, not
`qemu-system-i386`. A guest kernel was unnecessary once the static
binary ran. `NETSURFRES` pointed at `nsres/`. The command was
`-f ram -b 8 -w 640 -h 480` with the staged `canvas.html`.
`tools/wd24-browser/patches/netsurf-fb-dump.patch` writes the ram
buffer after three seconds when `WD24X_FB_DUMP` is set. The dump was
307200 bytes, sha256
`7529e449c486f60726c39fea3a62e723f5f8fd71174f1a175a0664172c17100b`,
71 distinct indexes. Index 0 (black) was 261177 pixels. The three
solid blocks landed on indexes 4 (1599), 35 (1445), and 200 (1652).
GNU `time -v` reported maximum resident set size 16400 kB. That is
the qemu-user process, so it is an upper bound on the guest. 16400 is
under 36864.

## Transfer

XMODEM at 1970 bytes/s. The stripped `nsfb` is the file to move.
3358656 / 1970 is 1704 seconds with 1776 bytes left, so 1705 seconds.
The tcz sizes below are the X frontends, not this binary.

| published file | size used | seconds at 1970 B/s |
|---|---|---|
| dillo.tcz 544K | 544*1024 = 557056 | 282, plus 1516 bytes, so 283 |
| fltk-1.3.tcz 500KB | 500*1024 = 512000 | 259, plus 1730 bytes, so 260 |
| netsurf.tcz 2.3M | 2.3*1024*1024 = 2411724 | 1224, plus 444 bytes, so 1225 |
| gtk2.tcz 2.3MB | same 2411724 | 1225 |

One mebibyte is 1048576/1970 = 532 seconds, plus 496 bytes, so 533
seconds. The stripped framebuffer binary measured above is the
transfer, not those tcz files.
