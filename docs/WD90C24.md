# wd90c24fb: native WD90C24A framebuffer

Goal: 640x480 at 8 bpp (256 colours) on the 755C's 10.4" TFT, with
BITBLT-accelerated fbcon, without ever leaving the panel blank.

## Stages

| stage | what | status | verified by |
|---|---|---|---|
| 1 | detect: Paradise lock test, CR2B/SR07/SR10/SR14, CR36/37 signature, PR1 memory size, PR18/PR19 panel state, 23C0 extended blocks (C24A) | done | unit tests (mock chip), QEMU negative probe |
| 2 | 640x480x8 packed mode through PR0(A) banking (4 KiB granules, 64 KiB window at A0000), shadow buffer, full save/restore, fallback | done | unit tests (registers, banking, flush); QEMU: `fake=1` fail-safe path, `.tcz` fallback to vga16fb |
| 3 | BITBLT (C24A/A2 only): fillrect/copyarea (fbcon scrolling) in video memory, self-tested at load, dropped on the first timeout | done | unit tests on the mock blitter (overlap in all directions, 300 random copies vs memmove, busy/stuck engine) |
| 4 | LCD/CRT: `output=` select (PR19), blank levels (1 = black picture; 2-4 = panel and backlight off: PR57 PNLOFF, PR4 bit 5, PR19 LCD, plus APM display standby), 100 ms power-up steps, sequenced restore | done | unit tests (write order, delays, restore after powerdown and output=crt); QEMU blank 1/0/4/0 round trip; panel needs hardware |
| 5 | APM suspend/resume: text mode (and BIOS outputs/panel power) handed back before suspend, VGA state re-saved, full mode set + redraw on resume, fb dropped if it fails; `text=1` to release the console before rmmod | done | QEMU: `fake=2` + `apm -s` round trip, then `text=1` + rmmod, text intact; real suspend needs hardware |
| 6 | Xfbdev acceleration: damage rectangles and BITBLT copies/fills from the X server (`WDFB_IOC_OPS`), instead of the 10 Hz whole-frame flush | done | QEMU: `fake=3` RAM model of video memory compared with the frame after a benchmark (0 bytes differ), `fake=4` + `fake_kbps` timings; real engine needs hardware |

## Fail-safe rules

* Only a chip with the `2`,`4` signature is driven unless `force=1` is given.
* Every register touched is saved first; any failure restores it and the
  module returns `-ENODEV` so the `.tcz` falls back to vga16fb or text.
* The probe writes only Paradise lock/scratch registers it restores (unit
  tests assert zero writes to timing, clock or memory-map registers).

## Parameters (`wd90c24fb.<name>=` on the boot line, or insmod)

| parameter | default | meaning |
|---|---|---|
| `enable` | 1 | 0: do nothing (the `.tcz` then loads vga16fb) |
| `trial` | 0 (also in `fb-wd90c24.tcz`) | seconds until text mode returns unless `keep` is set; boot with e.g. `wd90c24fb.trial=30` to try a risky setting |
| `keep` | 0 | `echo 1 > /sys/module/wd90c24fb/parameters/keep` during a trial |
| `output` | auto | `lcd`, `crt` or `both`: select outputs at load (C24 only); `auto` keeps the BIOS/Fn+F7 choice |
| `accel` | 1 | use the BITBLT engine if its self-test passes |
| `force` | 0 | also drive WD90C26/C30/C31/C33 (86Box bench) |
| `probe_only` | 0 | log chip, memory and panel state, load nothing |
| `text` | (write-only) | `echo 1 > /sys/module/wd90c24fb/parameters/text`: restore text mode and release fbcon now. fbcon holds a module reference while bound, so do this before `rmmod` (rmmod alone answers "Resource temporarily unavailable") |
| `xaccel` | 1 | offer mmap clients the damage/BITBLT ioctls (writable at run time; 0 = an X server started afterwards gets the 10 Hz whole-frame flush) |
| `apm_blank` | 1 | blank levels 2-4 also ask the BIOS for APM display standby (needs a kernel with `CONFIG_APM_DISPLAY_BLANK`; without it the PNLOFF sequence alone is used) |
| `stats` | (read-only) | `cat /sys/module/wd90c24fb/parameters/stats`: bytes and rectangles copied to video memory, BITBLT fills/copies, ioctls, whole-frame flushes, time spent copying (`flush_us`) and in the ioctl (`ioctl_us`), `accel`, `client` (an X server sends ops) |
| `fake` | 0 | testing only: 1 = treat any VGA as a C24 (QEMU fail-safe test); 2 = also skip the self-tests so the driver goes live on QEMU's VGA (suspend/resume test); 3 = also emulate the BITBLT engine on a RAM model of video memory, compared with the frame by `verify`; 4 = engine ops take no time and are not modelled (timing runs: the real engine works alongside the CPU) |
| `fake_kbps` | 0 | testing only, with `fake`: model a video-memory bus of this many KiB/s (busy-wait per row copied; QEMU maps A0000 as RAM, so copies are otherwise free) |
| `verify` | (read-only) | testing only (`fake=3`): number of bytes where the model of video memory differs from the frame |

## How stage 2 works

* Mode: XFree86's 256-colour settings (CR13 = 0x50, CR14 = 0x40, CR17 =
  0xE3, PR4 = 0x01, PR31 = 0x5C, PR30A = 0xC1) at the standard 640x480
  25.175 MHz timing (clock 0, PR68 bits 4:3 = 01). With the LCD on, PR11
  (CRTC locks) is left as the BIOS set it, as XFree86 did; the panel keeps
  its own timing.
* Clocks: only PR68 bits 4:3 (VCLK select) change, and they are restored
  with everything else; MCLK (PR68 bits 2:0, PR69) is never written, so
  the BIOS memory clock stays. The ROADMAP's 44.3 → 55 MHz MCLK raise is
  deliberately not done: it needs a measured stable value on a real 755C.
* Memory: PR1 bit 3 clear, so PR0(A) offsets the whole 64 KiB window in
  4 KiB steps; the frame is 300 KiB linear (y * 640 + x).
* Drawing: fbcon and `write()` go to a 300 KiB shadow (sys_* helpers);
  each operation copies its rectangle to the window, one row per lock
  hold. `mmap()` gets the shadow; see "X: damage and BITBLT" for how it
  reaches the screen. Scrolling copies the whole screen (stage 3 replaces
  this with the BITBLT engine).
* BITBLT: XFree86's wd90c31BitBlt register sequence (0x23C0 block 1,
  0x23C2 writes with the index in bits 15:12): linear source/destination
  offsets, pitch 640, DIM_X/DIM_Y in pixels, ROP SRC or XOR, fill from the
  foreground colour. A destination after the source runs backwards (start
  at the last pixel, CNTRL1 bit 10). fbcon's fills and copies go to the
  shadow (CPU) and to video memory (engine); the CPU waits for the engine
  before it next writes the window. Load-time self-test: fill and copy a
  64x4 block at 384 KiB (off screen) and read it back through the window.
* Order: save (vgastate: registers, fonts, text, palette; Paradise state)
  under the console lock, `register_framebuffer()` (fbcon takes over and
  vgacon stops touching the CRTC), mode set, banking self-test (PR0(A)
  read-back and four markers at 0/32K/64K/256K), then go live. Failure at
  any step restores text mode before fbcon gives the consoles back.

## Blank levels

`/sys/class/graphics/fb0/blank`, `FBIOBLANK` (X's screen saver / DPMS),
fbcon's console blanking:

| level | what the driver does |
|---|---|
| 0 `UNBLANK` | everything below undone: APM display standby left (palette and picture redrawn, since the BIOS may touch the chip), panel powered up in XFree86's order with the 100 ms steps (PR19 LCD on, PR4 panel signals, PR57 PNLOFF on = backlight), screen on |
| 1 `NORMAL` | black picture only (SR01 screen off); panel and backlight stay on, so unblanking is instant |
| 2 `VSYNC_SUSPEND`, 3 `HSYNC_SUSPEND`, 4 `POWERDOWN` | black picture, then panel off: PR57 bit 2 = 0 (PNLOFF: the CCFL inverter, i.e. the backlight), PR4 bit 5 (panel signals tristated), PR19 bit 4 = 0 (LCD interface off); then, if the kernel has `CONFIG_APM_DISPLAY_BLANK` and `apm_blank=1`, APM "display standby" through the BIOS (`console_blank_hook`) |

Why the backlight stayed lit before: PR57 bit 2 only drives PNLOFF while
PR19 bit 4 (LCD enable) is still set (PARADISE.TXT). The old code cleared
PR19 first, as the XFree86 sources are often read, so its PR57 write did
nothing. Power-down now goes PNLOFF → signals → LCD, the reverse of
power-up. The APM call is a second, independent way: the 755C BIOS
switches the panel and backlight off itself. The CRT (if enabled) is
blanked by the screen-off bit at every level; DPMS sync control for the
CRT is not implemented.

## X: damage and BITBLT (stage 6, `wd90c24fb_ioctl.h`)

Without help, an mmap client's frame is copied whole, 10 times a second,
over the VL-bus, whether anything changed or not: on a 755C that is
3 MB/s of slow video-memory writes with interrupts off per row, about a
third of the CPU (QEMU model at 8 MiB/s: 27 % with X idle), and the
picture still only changes 10 times a second.

tc32's Xfbdev (tinycore-32-ram `gfx/patches/tinyx/0003`, `0004`) instead
asks `WDFB_IOC_CAPS` and then sends `WDFB_IOC_OPS` batches:

* `DAMAGE x,y,w,h`: the client drew there; copy it from the shadow. Sent
  before the server sleeps, merged into as few rectangles as the region
  allows, and paced (the next update waits at least twice as long as the
  previous one took, minimum 15 ms), so a client drawing flat out still
  leaves the CPU half free and never has more copied than it changed.
* `COPY sx,sy → x,y,w,h`: screen-to-screen copy (scrolling, window moves,
  CopyArea), sent *before* the server copies the shadow, so video memory
  still holds the source; done by the BITBLT engine, no bus copy.
* `FILL x,y,w,h,colour`: solid fill (window backgrounds, clears,
  XFillRectangle), sent after the server filled the shadow; engine.

Only CopyArea, PolyFillRectangle, window moves and background fills use
the engine (an operation that fills and then draws on top, like
ImageText, is just damage). Copies under 1024 and fills under 2048 pixels
go as damage: cheaper than an engine round trip. If the engine is lost
(timeout) the ioctl returns `WDFB_LOST`, the driver redraws, and the
server asks again (damage only). Any error in a batch puts the driver
back to the 10 Hz flush, so the screen never freezes. `xaccel=0` turns
the ioctls off; `TC32X_NOWDACCEL=1` in Xfbdev's environment ignores them.

QEMU (`-icount shift=4`, about a DX4-100; `fake_kbps=8192` = an 8 MiB/s
VL-bus window; tinycore-32-ram `tests/gfx-bench.py`, ops/s, higher is
better):

| test | old: 10 Hz flush | new, damage only (`fake=2`) | new + BITBLT (`fake=4`) |
|---|---|---|---|
| X idle, CPU busy | 26.8 % | 0.1 % | 0.2 % |
| scroll 600x403 (CopyArea + fill + text) | 125.9 | 116.6 | 142.5 |
| fill 200x150 | 590.1 | 547.6 | 709.5 |
| text 80 columns | 671.1 | 628.6 | 626.8 |
| move a 300x200 window | 235.4 | 196.8 | 210.0 |
| bytes over the bus, scroll test | 10.8 MB | 7.1 MB | 2.2 MB |
| picture updates | 10/s, whole frame | every change, paced | every change, paced |

The old path's ops/s look good because it drops frames: the screen shows
a tenth of a second's worth at a time. `fake=3` runs the same with a RAM
model of the engine and checks it against the frame afterwards (0 bytes
differ after all four tests).

## Hardware cursor (stage 7, on by default)

`wd90c24fb.hwcursor` (default 1; `=0` turns it off) offers Xfbdev `WDFB_CAP_CURSOR` / `WDFB_IOC_CURSOR`:
a 32x32 two-colour cursor in register block 2 (WD90C31 data book section
8; the C24A has the same block). The pattern sits in off-screen memory at
0x50000 (above the 300 KiB frame, below the BITBLT self-test area).
Moving the pointer is then two register writes instead of X redrawing the
cursor and the driver copying it over the ISA bus. Without the parameter
(or with `TC32X_SOFTCURSOR=1` for Xfbdev) X uses its software cursor.

- `hwc_xoff`, `hwc_yoff`: calibration if the chip shows the cursor shifted.
- `cursor_test` (no X running): write 1/2/3 to show a
  test arrow (white with a black outline, tip = hot spot) at the centre /
  top-left / bottom-right; 0 hides it. Reading dumps registers 0-8.
- `stats` gains `cursor=` (ioctl calls) and `hwcursor=` (shown now).

Not verified on the chip yet (QEMU has no cursor block): the unit tests
check the register sequence and pattern layout against the data book.

## Ioctl overhead

Measured on the 755C: `ioctl_us - flush_us` = 0.64 s over 75278 ioctls,
about 8.5 us per call. The time is the ISA copy itself, and nearly every
call carries one rectangle (paced damage), so batching more rectangles per
call would not help.

## Colour expansion (stage 8, `cexp`, on by default)

Damaged rows holding at most two colours (text, glyph runs, stipples,
1 bpp images: whatever X drew) are sent as one BITBLT with source
"monochrome from host" (data book 9.14), one bit per pixel through port
23C4, instead of a byte per pixel through the memory window. It works on
the damage the driver already gets, so every X text path benefits without
TinyX changes; bands of rows (up to 1024 port words per lock hold) batch
glyph runs, rows with more colours are copied as before.

The data book is ambiguous for packed mode ("four low-order bits are
expanded to four 8-bit pixels", but writes come "in 32-bit groups"), so
the word format is a variant 0-11: 4/8/16 pixels per word, most or least
significant bit first, rows padded to words or doublewords. At load the
driver probes them off screen (0x60000) against a CPU reference, writing
each word only while the engine is still busy (an unexpected write to the
port could hold the bus), then times a port write against a memory byte.

- `cexp=1` (default): on if a variant passes and the estimate says it is
  faster; `cexp=2`: on if a variant passes; `cexp=0`: off.
- `cexp_var=N`: only that variant (skip the probe of the others).
- `cexp_test`: write 1 to re-run the probe at any time (nothing on screen
  changes); read it for the per-variant PASS/FAIL report and timings.
- `stats`: `cexp=` bands, `cexp_px=`, `cexp_words=`, `cexp_var=` in use (-1 off).

## Needs real-hardware verification

* The CR36/37 signature, PR1 memory size and PR18/PR19 values on a 755C
  (load `wd90c24-probe.tcz`, send `dmesg | grep wd90c24fb`).
* The mode on the panel: picture position, colours (6-bit DAC to the TFT),
  no flicker, with the LCD only, the CRT only, and both (Fn+F7).
* Text mode after `text=1` + `rmmod wd90c24fb` and after a trial ends: fonts, colours,
  cursor, BIOS panel stretch.
* Speed of a full-screen scroll over the window (expected tens of ms
  with `accel=0`, a few ms with the BITBLT engine).
* dmesg says "BITBLT self-test passed"; scrolling, the XOR text cursor and
  clears look right with `accel=1` and match `accel=0`.
* Suspend/resume and Fn-key display switching while the fb is live.
* Blanking: `echo 1 > /sys/class/graphics/fb0/blank` must black the
  picture with the backlight on; `echo 4` (powerdown) must turn the panel
  *and its backlight* off, with and without the APM kernel
  (`apm_blank=0` tests PNLOFF alone); `echo 0` must bring the picture
  back after ~200 ms. `setterm -blank 1` likewise. `output=crt`/`both`
  with an external monitor.
* X: `stats` while scrolling in an rxvt (`ls -lR /`): `client=1`, `full`
  stays put, `copies` climbs, no `BITBLT engine timed out` in dmesg, and
  the picture matches `xaccel=0` (no stale or smeared areas).
* Note: restore puts PR19 back as it was at load, so a display switched
  with Fn+F7 while the fb was live returns to the load-time choice.

  Notable facts: PR1 bit 3 = 0 makes PR0(A) offset the whole 64 KiB window;
  PR1B (CR34) is write-only; index-control bit 13 reads 1 for a register
  block that does not exist (used to tell C24A from C24).

## Bench: 86Box (manual)

86Box emulates the Paradise WD90C11/C20/C30/C31 (`vid_paradise.c`), not
the C24. The Paradise core, PR0(A) banking, the 256-colour path and (C31)
the BITBLT block are shared with the C24A, so a C30/C31 card is the closest
bench:

1. 86Box with a 486 machine, 16+ MB, video card "Paradise WD90C30" or
   "WD90C31" (the card ROM must be in `roms/video/`), floppy A: = `out/tc755.img`,
   IDE disk = `out/tc755-tcz.img`.
2. Boot, `tce-load -i wd90c24-probe`: dmesg should name the chip (C30/C31,
   signature `3`,`0`/`3`,`1`) and the memory size.
3. From stage 2: `insmod .../wd90c24fb.ko force=1` exercises banking, the
   mode set, restore on `text=1` + `rmmod` (or trial end), and (C31) the
   blitter self-test.
